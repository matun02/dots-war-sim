## 設計の進め方

### Step 1: 既存実装の現状把握

Phase 2 で変更・拡張する可能性がある全ファイルを Read で確認する。
最低限以下を読むこと（他にも必要と判断したファイルは追加で読む）:

- `packages/core/src/sim/types.ts` — 型定義
- `packages/core/src/sim/constants.ts` — 定数
- `packages/core/src/sim/tick.ts` — tick 処理順
- `packages/core/src/sim/steps/` 配下 — 各ステップの実装
- `packages/core/src/pathfinding/astar.ts` — A* 実装（地形コスト定義）
- `apps/web/src/game/ai/controller.ts` — AI v0 実装
- `apps/web/src/game/render/` 配下 — 描画レイヤ
- `apps/web/src/game/input/commands.ts` — 入力ハンドラ
- `apps/web/src/App.svelte` — 画面遷移・ゲームループ統合
- `apps/web/src/ui/Title.svelte` — タイトル画面
- `packages/maps/` — マップスキーマ・ローダー・既存マップ

現状把握の目的:
- 各タスクで変更が必要なファイル・関数を特定する
- 既に実装済みの部分（例: `UNIT_STATS.heavy`, `TERRAIN_COST_HEAVY`）を把握する
- タスク間の依存関係を確定する
- 2 ディレクトリ制限（CLAUDE.md §7.2）を満たすタスク分割を検証する

### Step 2: 各タスクの詳細設計

`future-phases.md` の概要 + `DESIGN.md` の仕様 + Step 1 の現状把握を元に、
各タスク（P2-T1〜T6）について以下を設計する:

| 項目 | 内容 | 導出元 |
|------|------|--------|
| **入力** | タスクが前提とする設計仕様・既存実装 | DESIGN.md の該当セクション |
| **作業内容** | 変更・新規作成するファイルと具体的な変更内容 | 現状把握 + DESIGN.md から導出 |
| **成果物** | 生成されるファイル一覧 | 作業内容から導出 |
| **受け入れ基準** | 機械的に検証可能な条件のチェックリスト | DESIGN.md の仕様 + テスト要件 |
| **見積** | 時間見積（h単位） | 作業内容の規模から判断 |

設計時の注意:
- **DESIGN.md に書かれている数値・仕様をそのまま使う**。独自に変更しない
- **既存実装で既に対応済みの部分は明記する**（例: A* の heavy 地形コストは実装済み）
- **タスク間の依存関係を明確にする**（例: P2-T3 は P2-T2 の成果物が必要）
- **2 ディレクトリ制限を満たすことを検証する**

### Step 3: テスト設計

各タスクのテスト計画を設計する:

- **単体テスト**: `packages/core` の純関数テスト（Vitest）
- **統合テスト**: tick 全体を通した動作テスト
- **E2E テスト**: Phase 2 完了後に実行する Playwright シナリオ（DESIGN.md §17.3 に追加分）

テスト設計時の注意:
- CLAUDE.md §4.3 の決定論要件に対応するテストを含める
- 既存テスト（132 件）との重複を避ける
- 境界条件（補給上限、地形境界等）を含める

### Step 4: 成果物の書き出し

以下のファイルを作成・更新する:

#### 4a. `TASKS.md` の更新

Phase 2 セクションを追加する。フォーマットは Phase 1 の既存形式を踏襲:
- M4 マイルストーン詳細
- タスク一覧テーブル
- ★次タスク（P2-T1）の詳細セクション
- 残タスク一覧

#### 4b. `future-phases.md` の更新

Phase 2 セクションを詳細化した仕様で拡充する。
既存の概要は削除せず、詳細を追記する形で更新する。

#### 4c. タスク実行プロンプトの生成

`.claude/archive/task-prompts/P2-T1-prompt.md` 〜 `P2-T6-prompt.md` を生成する。

各プロンプトは `skill-next-task-prompt.md` のテンプレートに準拠し、自己完結型で作成する。
既存プロンプト（`P1-T11-prompt.md` 等）のフォーマットと詳細度を参考にする。

プロンプト生成時の注意:
- 「現在の状態」セクションには Step 1 で確認した **実際の** ファイル状態・テスト件数を反映
- 各プロンプトの依存タスクを明記（例: P2-T3 は P2-T2 完了が前提）
- P2-T2〜T6 の「現在の状態」は、直前タスクが完了した想定で記載する
  （コミットハッシュ等は `{前タスクのcommit}` のようなプレースホルダで可）

### Step 5: commit & push

全ての変更を 1 コミットにまとめる:

```
docs(phase2): add Phase 2 detailed task specs and prompts (P2-design)
```

commit 前に以下を確認:
- `pnpm -r typecheck` — ドキュメントのみの変更なので不要だが念のため
- 生成したプロンプトの整合性チェック（タスク間参照が正しいか）

### Step 6: ユーザーに報告

生成したファイル一覧と、P2-T1 から開始するためのプロンプトファイルパスを提示する。

## 制約（★MUST）

- **情報を削除しない**: 既存の記載は残す。概要と詳細を併記して良い
- **意味を変えない**: DESIGN.md の設計意図・数値・仕様を勝手に変えない
- **設計思想を変更しない**: MVP 最優先・過剰設計禁止・決定論最優先を維持
- **Claude Code 向け最適化を優先**: プロンプトは機械的に処理しやすい構造にする
- **表現は端的かつ誤解のない**: 曖昧な表現を避け、具体的な型名・ファイルパス・数値で記述
- **2 ディレクトリ制限**: 各タスクが触るディレクトリが 2 つ以下であることを確認（CLAUDE.md §7.2）
- **既存テスト（132 件）を壊す変更を設計に含めない**
- **推測で仕様を補完しない**: DESIGN.md に記載がない仕様が必要な場合はユーザーに確認する
