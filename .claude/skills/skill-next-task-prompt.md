# 次タスクプロンプト生成 + /compact スキル

タスク完了後に、TASKS.md から次の未完了タスクを特定し、
新しいセッション向けの自己完結型プロンプトを生成して `/compact` を実行するスキルです。

「次タスクのプロンプトを作成して」「次のタスク用のプロンプトを生成して」等と指示されたときに使ってください。

---

## なぜこのスキルが必要か

各タスクは新しい Claude Code セッションで実行される。
新セッションはこれまでの会話コンテキストを持たないため、
プロンプト 1 つだけで全ての前提条件・現在の状態・仕様・テスト計画を伝える必要がある。
このスキルはその「自己完結型プロンプト」を機械的に組み立てる。

---

## 手順

### 1. 次の未完了タスクを特定する

`.claude/TASKS.md` を読み、**「★次タスク」セクション**を探す。
そこに記載されたタスク ID とタスク名を記録する。

### 2. 現在の状態を収集する

以下のコマンド・ファイルから情報を集める:

| 情報 | 取得方法 |
|------|----------|
| 完了済みタスク一覧とコミットハッシュ | TASKS.md の「完了済みタスク」表を参照 |
| 全テスト件数 | `pnpm -r test` の出力から各パッケージのテスト数を拾う、または直近の既知の件数 |
| 次タスクが触るファイルの現在の中身 | Read ツールで空ステップ・既存コード等を確認 |
| 次タスクが依存するファイルの API | 型定義（types.ts）、既存 render 関数のシグネチャ等 |
| パッケージの依存関係 | 関連する package.json |
| App.svelte の現在の状態 | Read で確認 |
| 最新コミットハッシュ | `git log --oneline -1` |
| Node / pnpm バージョン | 直近で確認済みの値を流用（大きく変わらない） |

**重要**: 次タスクの仕様に登場するファイルを全て読むこと。
空実装のファイルは「空実装」と明記し、シグネチャを記載する。
既に実装済みのファイルは主要 API を記載する。

### 3. DESIGN.md から関連セクションを特定する

TASKS.md のタスク定義に「入力: `DESIGN.md` 章 X」と書かれている場合、
そのセクション番号をプロンプトの冒頭指示に含める。

### 4. プロンプトを組み立てる

以下のテンプレートに従い `.claude/archive/task-prompts/{TASK_ID}-prompt.md` に書き出す。

---

## プロンプトテンプレート

```markdown
## 事前にコンテキスト把握（必須）
@.claude/CLAUDE.md @.claude/DESIGN.md @.claude/TASKS.md @.claude/SETUP.md を読んでください。
特に CLAUDE.md §{関連セクション} と DESIGN.md §{関連セクション} を厳密に守ること。

## 現在の状態
- M{N}（{マイルストーン名}）{完了 or 進行中}。P1-T1〜T{最後の完了タスク} 全て green。
  {完了済みタスクごとに:}
  - commit `{hash}`: {タスク概要} — `{主要ファイルパス}`
- `pnpm install`, `pnpm -r typecheck`, `pnpm -r test`, `pnpm lint` すべて green。
- テスト件数: {パッケージ別内訳} = 合計 {N} 件。
{次タスクに関連する現在のファイル状態を箇条書きで詳述:}
- `{ファイルパス}` に {何が定義/実装されているか}。
  - {重要な型・定数・API の名前}
- `{ファイルパス}` — {空実装 or 実装済み}（`{シグネチャ}`）
- {App.svelte の現在の状態}
- Node {バージョン}, pnpm {バージョン} が PATH 通済。
- `.claude/settings.json` で Edit/Write 後に自動で prettier・eslint --fix が走る hook が有効。

## これからやるタスク
**{TASK_ID}: {タスク名}**

{タスクの目的を 1〜2 文で}

### 仕様

{TASKS.md のタスク定義をベースに、以下を追加・補強:}

#### 1. {ファイル/モジュール名} — {役割}

```ts
// 関数シグネチャ + コメントで仕様を説明
// 既存の型（types.ts）を正確に参照
// DESIGN.md の該当仕様を反映
```

{必要に応じてセクション 2, 3, ... を追加}

### 実装要件
{CLAUDE.md の規約から、このタスクに特に関連するものを列挙:}
1. **{規約}** — {根拠}（CLAUDE.md §{N}）
2. ...

### テスト計画

#### `{テストファイルパス}`
- {テストケースの説明}
- {テストケースの説明}
- ...

### 禁止事項
* {このタスクで特に注意すべき禁止事項}
* 既存テスト（{パッケージ別件数}）を壊す

### 受け入れ基準
- [ ] {機械的に検証可能な条件}
- [ ] `pnpm -r typecheck` 通る
- [ ] `pnpm lint` 通る
- [ ] `pnpm -r test` 通る（既存 {N} 件 + 新規テスト全て green）

### 着手前に提示してほしいこと
CLAUDE.md §7.1 の規約に従い、実装に入る前に以下を提示してください:
1. 変更予定ファイル一覧
2. テスト計画（どんなケースを書くか）
3. 想定される影響範囲

承認したら実装に進んでください。

### 完了後のコミット
完了したら以下の形式でコミット (.claude/skills/skill-commit-convention.md 準拠):

```
{type}({scope}): {subject} ({TASK_ID})
```

[本文に{成果物}の要点を簡潔に]

コミット前に `pnpm -r typecheck && pnpm -r test && pnpm lint` を必ず通すこと。
コミット後に `git push` すること。
完了後に `.claude/skills/skill-task-completion.md` に従い TASKS.md / CLAUDE.md を更新してコミット・push すること。
```

### 5. プロンプトの品質チェック

書き出したプロンプトを読み返し、以下を確認する:

- [ ] **自己完結性**: このプロンプトだけで、CLAUDE.md/DESIGN.md/TASKS.md を読んだ新セッションが着手できるか
- [ ] **現在の状態の正確性**: コミットハッシュ、テスト件数、ファイルの存在状態が実際と一致するか
- [ ] **仕様の具体性**: 関数シグネチャ、定数値、型名が types.ts や DESIGN.md と整合しているか
- [ ] **テスト計画の網羅性**: 正常系 + エラー系 + 境界条件がカバーされているか
- [ ] **禁止事項の明確性**: CLAUDE.md の規約からこのタスクに関連するものを漏れなく列挙しているか

### 6. ユーザーに報告する

生成したプロンプトファイルのパスを提示し、内容の要約（どのタスク向けか、主な変更点）を伝える。

### 7. /compact を実行する

プロンプト生成が完了したら、会話のコンテキストを圧縮するために `/compact` を実行する。

---

## 注意事項

- **TASKS.md の指示文サンプルはあくまで骨格**。プロンプトには現在の実際のコード状態を反映させること
- **前のタスクのプロンプト** (`.claude/archive/task-prompts/` 内) を参考にすると、フォーマットの一貫性が保てる
- **仕様が曖昧な場合はユーザーに確認**してからプロンプトに反映する。推測で補完しない
- 全ての未完了タスクがこの形式を必要とするわけではない。簡単なタスク（docs のみ等）はより軽量でよい
